# Нежелательные письма подтверждения подписки 24 ноября 2026

## Вывод и границы подтверждения

Найден конкретный публичный путь отправки письма на адрес посетителя:

`Footer / NewsletterBanner / newsletter status page` →
`NewsletterForm` → Server Action `subscribeToNewsletter` →
`sendNewsletterConfirmation` → `sendTransactionalMail` → SMTP или Resend.

Немецкое название формы — «Praxistipps für Ihre Sichtbarkeit», кнопка —
«Anmelden». Общий Footer подключён и к `/branchen/arztpraxen`; отдельного
медицинского обработчика отправки писем у страницы нет. Server Actions
отправляют POST на текущий URL страницы, поэтому в HTTP-логе это именно
`POST /branchen/arztpraxen`, а не обязательно `/api/newsletter/...`.

Получатель брался из `formData.email`, после trim/lowercase и Zod-проверки.
Отправлялось **письмо Double-Opt-In**, а не выпуск маркетинговой рассылки.
Темы: DE `Bitte bestätigen Sie Ihre Newsletter-Anmeldung`, EN
`Please confirm your newsletter subscription`, RU
`Подтвердите подписку на рассылку`. Текст/тема шаблонные; ссылка подтверждения
подписана прежним AUTH_SECRET. Newsletter использует NEWSLETTER_FROM или
существующий fallback отправителя; SMTP-ветка использует общий Hostinger
транспорт. Общий транспорт и его настройки не изменены.

До исправления были валидация e-mail/локали, honeypot `website` и запрет
повторного письма уже подтверждённому подписчику. Для нового адреса создавалась
pending-запись, для существующей pending обновлялась локаль; **оба случая
всегда вызывали отправку**. CAPTCHA и лимитов здесь не было. Наличие
Double-Opt-In не предотвращало злоупотребление самым первым письмом.

### Сопоставление с предоставленным CSV

- 769 строк экспорта, 64 POST всего; 55 POST на медицинскую страницу за
  весь интервал экспорта, с 38 разных IP.
- На **24.11.2026 по Europe/Berlin** приходится 49 таких POST, с 34 IP;
  все получили HTTP 200. Начало экспорта захватывает и вечер 23 ноября.
- `2026-11-24T19:36:53Z` действительно есть в CSV: это **20:36:53 в Германии**,
  совпадающий с приведённым владельцем примером.
- HTTP 200 у Server Action не доказывает SMTP-отправку: прикладная ошибка
  тоже может возвращаться внутри React-ответа с HTTP 200.
- В CSV нет тела запроса, Next-Action ID, адреса получателя, mail ID и
  результата SMTP. Поэтому каждую из 13 почтовых записей нельзя независимо
  связать с action только по этому файлу. Их корреляция за 1–2 секунды
  предоставлена владельцем и согласуется с найденным уязвимым путём.

В репозитории сохранён только обезличенный агрегат с SHA-256 исходного файла:
`docs/audits/2026-11-24-newsletter-http-log-summary.json`. IP, полные User-Agent,
чужие адреса и сам исходный лог не копировались в Git.

## Серверное отключение

Используется существующая общая таблица Prisma **Settings**:

| Поле | Значение для первого деплоя |
|---|---|
| `Settings.key` | `newsletter.signup.enabled` |
| `Settings.value` | **`false` — JSON boolean**, не строка |

Отсутствующая запись также означает **выключено**. Разрешение даёт только
JSON boolean `true`; строки `"true"`, `"1"`, null и ошибки чтения не включают
отправку. Это **не переменная окружения** `NEWSLETTER_SIGNUP_ENABLED`.
Новые переменные SMTP/Hostinger не вводились и секреты не менялись.

Проверка выполняется в action, повторно под блокировкой при резервировании
и перед подготовкой письма. Старый HTML, ручной POST, изменение клиентского
JS или значение формы не обходят серверный флаг. Уже начатую/принятую SMTP
операцию отменить этим флагом нельзя.

UI получает доступность через `/api/newsletter/status` с `no-store`, поскольку
публичные страницы кешируются статически. Первоначальный HTML показывает
понятное DE/EN/RU сообщение о временной недоступности и не содержит форму
подписки. При выключенном флаге или ошибке проверки UI остаётся закрытым.
Обработчик не доверяет этому клиентскому состоянию.

Команды оператора, **не запускались против рабочей БД**:

```powershell
node --conditions=react-server --import tsx scripts/newsletter-signups.ts status
node --conditions=react-server --import tsx scripts/newsletter-signups.ts disable
# Только после проверок и отдельного решения о включении:
node --conditions=react-server --import tsx scripts/newsletter-signups.ts enable
```

Они используют настроенную в окружении БД. CLI требует установленный `tsx`;
если production установлен без devDependencies, настройку можно задать через
существующий PostgreSQL-инструмент оператора:

```sql
INSERT INTO "Settings" ("id", "key", "value", "updatedAt")
VALUES (gen_random_uuid()::text, 'newsletter.signup.enabled', 'false'::jsonb, now())
ON CONFLICT ("key") DO UPDATE SET "value" = 'false'::jsonb, "updatedAt" = now();
```

SQL приведён как инструкция и здесь не выполнялся против рабочей БД.
Не запускайте seed/db:push для переключения флага и не удаляйте состояние лимитов.
Schema/migrations не менялись: используются уже существующие модели.

## Защита при повторном включении

- Переиспользуются `TurnstileField` и серверный `verifyTurnstileToken`, новая
  action-метка — `newsletter_signup`. Для newsletter обе ключевые настройки
  Turnstile обязательны; development bypass контактных форм не даёт разрешения
  на newsletter-отправку. Контактная валидация/метки/поведение не изменены.
- Проверяются успешность Siteverify, action, production hostname; отсутствующий,
  неправильный и чужой token не допускают письмо. Honeypot сохранён.
- **Один адрес — одна попытка за скользящие 24 часа** после нормализации.
- **Общий предел — 5 попыток за скользящий час и 20 за скользящие 24 часа**,
  независимо от IP, процесса и страницы с формой.
- Резерв хранится в `Settings` под ключом
  `newsletter.signup.delivery-reservations.v1`: версия, время PostgreSQL и
  SHA-256 нормализованного e-mail. В журнале нет исходных адресов/IP;
  собственно подписчики остаются в прежней NewsletterSubscriber.
- Одна короткая PostgreSQL-транзакция с transaction-scoped advisory lock
  сериализует проверку/запись лимитов и создание pending-записи. В том числе
  защищён первый конкурентный запрос, когда строки лимитов ещё нет.
- SMTP вызывается **после коммита резервирования**, вне транзакции. Сбой SMTP,
  разрыв соединения или остановка процесса не возвращают квоту автоматически:
  результат доставки мог быть неопределённым. Повреждённое состояние лимитов
  вызывает отказ, а не тихий сброс. Запись ограничена 20 резервами; старые
  метки удаляются при следующем успешном резервировании.
- Для legacy pending без журнала учитывается также `createdAt`: свежая запись
  не получает повторное письмо в первые сутки. Историческое точное время
  предыдущих повторных отправок старый код не сохранял.
- Новый адрес: pending + одно DOI-письмо. Pending после cooldown: допускается
  новое DOI в пределах общего бюджета. Confirmed: `already`, без SMTP и квоты.
- Подтверждение ранее отправленных токенов и отписка не зависят от нового
  выключателя. Контактные уведомления, автоответы и другие почтовые сценарии
  не выключаются глобально.

Использованы [transaction-level advisory locks PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)
и существующая [серверная проверка Turnstile](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
Защита лимитов не полагается только на одноразовость CAPTCHA.

## Проверка штатных форм перед повторным включением

1. Первый разрешённый деплой выполнить с `newsletter.signup.enabled=false`
   или отсутствующей записью; все старые процессы приложения должны быть
   заменены новым кодом. Проверить runtime status=false и DE/EN/RU notice.
2. С выключенной подпиской проверить обычную заявку на главной, `/kontakt`
   и бесплатный аудит: валидация, Turnstile, сохранение лида, admin notification,
   клиентский автоответ, повторная отправка того же submissionId без дубля.
   Локально это проверяется исключительно через SMTP-stub; production-доставку
   позже проверяет оператор на собственных контрольных адресах.
3. Проверить ранее выданный валидный DOI и отписку контрольного подписчика.
   Не удалять реальные pending-записи и не сбрасывать квоты ради теста.
4. Сверить обе Turnstile-настройки и hostname. Изменение публичного site key
   требует новой сборки; на сервере нужно видеть `action=newsletter_signup`.
   Дождаться прекращения потока злоупотреблений, проверить журнал отправок.
5. После отдельного решения включить JSON boolean `true`. На собственном
   контрольном адресе проверить одно DOI, повтор без второго письма,
   подтверждение и отписку. Следить за новыми SMTP-записями и отказами лимитов;
   при повторении проблемы вернуть `false`, без отключения всей почты сайта.

Публикация и production-проверки в эту задачу не входят. Локальный фикс ещё
не прекращает отправки старой опубликованной версии. Оценка: **лучше** —
серверное отключение и ограниченная защищённая подписка вместо неограниченного
DOI-отправителя. Нет обещания полного исключения злоупотреблений или подтверждения
реальной доставки в почтовый ящик; до включения подписка намеренно недоступна.
