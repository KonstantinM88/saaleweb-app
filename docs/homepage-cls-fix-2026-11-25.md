# Главная: CLS, контраст и полоса прогресса — 25.11.2026

## Подтверждение

Повторный PageSpeed Insights mobile на опубликованной главной воспроизводит
CLS **0,2506975**, Performance 83, Accessibility 97, Best Practices/SEO 100.
Это лабораторный замер до исправления, не CrUX и не результат локального патча.
[Сохранённый ответ без API-ключа](audits/2026-11-25-psi-before-cls-fix.json).

Единственный значимый CLS-элемент — `.hero-gradient-field`. Google также
помечает два загруженных шрифта, но это подсказка корреляции. Контрольный
локальный тест с задержкой шрифтов на 1800 мс и полностью полученным HTML
показал CLS 0 и неизменную высоту Hero до/после загрузки шрифтов.

Зато при постепенном получении HTML проблема воспроизводится: локальный
proxy делит тот же production HTML перед первым текстовым элементом Hero,
передаёт начало и задерживает остаток на 3000 мс. PerformanceObserver
устанавливается в head до первой отрисовки. Исходный код даёт CLS
**0,1604050** на viewport 412×823; основной источник — фон Hero. Небольшой
дополнительный сдвиг навигации обусловлен появлением desktop scrollbar в
этом браузерном режиме. Это стресс-сценарий постепенной передачи документа,
а не повторение всех условий PageSpeed/Slow 4G.
[Исходный локальный замер](audits/2026-11-25-cls-stream-before.json).

## Исправление

1. `globals.css`: вместо `inset: -16%` у `.hero-gradient-field` теперь
   `inset: -160px -16%`. Вертикальный отступ не зависит от изменяющейся
   высоты ещё загружаемой секции; боковой запас, градиент и transform-анимация
   сохраняются. Высота текста/контента не фиксируется искусственно.
2. `BeforeAfter.tsx`: неактивная кнопка «Vorher/Nachher» использует
   `text-gray-700` вместо `text-muted` на фоне `#f2f0f6`. PageSpeed подтвердил
   прежний контраст 4,27:1 вместо требуемых 4,5:1 для 14px текста.
   Правка общая для DE/EN/RU и обоих состояний переключателя.
3. `ScrollProgress.tsx`: полоса имеет постоянную полную ширину и меняется
   через `scaleX`, а не layout-свойство width. На нулевой позиции прокрутки
   больше не запрашивается высота документа; сохраняются rAF, resize,
   восстановленная прокрутка и passive listener.

Сопоставление публичного chunk `9861-4335f31c7f1be7fc.js` с исходниками
подтвердило ScrollProgress для ~1,5 мс forced reflow; ещё ~1,2 мс относится
к Navbar. Unattributed и сторонний GTM не объявляются исправленными только
по этой локальной правке. Рекомендация Google — отделять layout reads/writes
и использовать compositor-friendly transform:
[CLS](https://web.dev/articles/optimize-cls),
[layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing).

## Замечание про 12 KiB legacy JavaScript

Совпадающие проверки Array.at/flat/flatMap, Object.fromEntries/hasOwn и
String.trimStart/trimEnd находятся в штатном Next.js
`node_modules/next/dist/build/polyfills/polyfill-module.js`. Это оценка
потенциальной экономии, не новая уязвимость и не JavaScript-ошибка сайта.
Внутренние файлы Next/webpack aliases не переписывались ради снятия аудита;
поддержка браузеров и зависимости не менялись.
[Официальные сведения Next.js](https://nextjs.org/docs/architecture/supported-browsers).

## Проверки и статус

Последовательно пройдены TypeScript, полный ESLint и production Webpack build
Next.js 16.4.6 (247 страниц). Существующее предупреждение Edge Runtime
не блокировало сборку. Зависимости и Next.js в этом исправлении не менялись.

На готовой сборке, без CSS override, тот же proxy-сценарий дал:

**0,1604050 → 0,0003866**. Это локальные цифры; публичный PageSpeed после

Три главные отвечают 200, имеют по одному H1, правильный self-canonical,

Изменения локальные, без коммита/push/деплоя, миграций, изменения
