# Аудит 157 URL «Не найдено (404)» в Search Console — 07.10.2026

## Что проверено

- В отчёте Search Console показано 157 URL с причиной `Не найдено (404)` и источником `Сайт`.
- Production sitemap содержит 234 канонических URL. Все 234 вернули HTTP 200.
- На этих страницах найдено 250 уникальных внутренних HTML-ссылок `href`. Все 250 вернули HTTP 200 без редиректов и 404.
- У 114 канонических страниц оставался автоматически созданный next-intl HTTP-заголовок `Link` с 456 hreflang-ссылками.
- В заголовках было 219 уникальных адресов: 81 отвечал 404, ещё 24 уже перенаправлялись существующими 308-редиректами.

## Подтверждённая причина

Для динамического `[slug]` next-intl подставлял текущий slug во все языковые пути. Это неверно для страниц, где DE, EN и RU используют разные slug. Например, английская страница `/en/industries/restaurant-website` объявляла русским hreflang несуществующий URL `/ru/otrasli/restaurant-website` вместо `/ru/otrasli/sayt-dlya-restorana`.

URL Inspection API подтвердил связь с отчётом Google:

- `https://saaleweb.de/ru/otrasli/restaurant-website`
- `coverageState: Nicht gefunden (404)`
- `pageFetchState: NOT_FOUND`
- последний обход: `2026-08-21T03:04:11Z`
- Google указал источниками `https://saaleweb.de/branchen/restaurant-website` и `https://saaleweb.de/en/industries/restaurant-website` — именно страницы, которые отдавали ошибочный HTTP hreflang.

3 октября middleware уже удалял конфликтующий заголовок для услуг и проектов. Исправление было неполным: отрасли, статьи и категории блога оставались открытым источником ошибочных URL.

## Исправление

1. `src/proxy.ts` удаляет автоматически созданный HTTP hreflang на всех динамических маршрутах с переводимыми slug:
   - услуги;
   - отрасли;
   - проекты;
   - статьи блога;
   - категории блога.
2. Правильные HTML hreflang и sitemap остаются источниками языковых связей.
3. `next.config.mjs` создаёт постоянные 308-редиректы для исторических cross-locale комбинаций отраслей, статей и категорий на соответствующий канонический URL того же языка.
4. Редиректы дедуплицируются, а конфликт источника с двумя разными целями останавливает сборку ошибкой.

Канонические URL, контент и sitemap не меняются. Исправление прекращает появление новых 404 из HTTP hreflang и даёт Google однозначный путь со старых ошибочных адресов на существующие страницы.

## Локальная проверка

- TypeScript: успешно.
- ESLint: успешно.
- Production build: успешно, сгенерировано 252 страницы.
- Sitemap: 234 URL.
- Проверено 183 динамических страницы: все вернули 200, ни одна не отдала конфликтующий HTTP hreflang; в HTML каждой осталось 3 или 4 корректных alternate-ссылки.
- Проверено 150 точных compatibility redirect: каждый источник вернул 308, каждая конечная страница — 200.
- Все 81 активный production 404 из ошибочных HTTP hreflang покрыты новым редиректом; несовпадающих целей нет.

## Действия после деплоя

1. Проверить, что все 234 sitemap URL по-прежнему отвечают 200.
2. Проверить отсутствие HTTP `Link` hreflang на динамических страницах с переводимыми slug.
3. Проверить, что ранее найденные 81 URL теперь отвечают 308 и приводят на канонический 200.
4. Один раз повторно отправить существующий `https://saaleweb.de/sitemap.xml` через Search Console API.
5. В интерфейсе Search Console открыть проблему `Не найдено (404)` и нажать `Проверить исправление`. Search Console API не предоставляет список URL этого отчёта и не запускает проверку исправления.

Число 157 не уменьшится сразу после деплоя: Google обновляет отчёт после повторного обхода старых адресов.
