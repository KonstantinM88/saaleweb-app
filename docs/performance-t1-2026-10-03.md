# T1: mobile PageSpeed, HTML и www

Дата: 03.10.2026. Измерены действующие канонические DE-страницы до публикации изменения www. Сырые компактные результаты PageSpeed сохранены в [`audits/2026-10-03-performance-mobile.json`](./audits/2026-10-03-performance-mobile.json). Это лабораторный замер, не полевые Core Web Vitals и не доказательство изменения позиции Google.

## Mobile PageSpeed

Для каждого URL выполнены три прогона PageSpeed Insights API v5 с `strategy=mobile` и категорией `performance`. Повторный ответ с одинаковым `Lighthouse fetchTime` исключён: всего потребовалось 11 API-запросов для девяти разных отчётов. Значения ниже — медиана трёх уникальных отчётов. API не вернул полевые CrUX-метрики ни для URL, ни для origin.

| Страница | Score | FCP | LCP | TBT | Lighthouse total byte weight |
|---|---:|---:|---:|---:|---:|
| `/` | 75 | 2,47 с | 3,77 с | 321 мс | 1,33 MB |
| `/leistungen/webdesign-halle` | 62 | 4,83 с | 7,69 с | 167 мс | 1,12 MB |
| `/leistungen/website-erstellen-lassen` | 62 | 4,82 с | 7,59 с | 142 мс | 1,12 MB |

У обеих страниц услуг LCP в отдельных прогонах менялся примерно от 1,84 до 7,7 с. Эти девять отчётов показывают проблему нестабильного лабораторного результата, но не доказывают, что конкретный компонент сайта каждый раз задерживает отрисовку на 7+ секунд. В диагностике одного дополнительного прогона GTM и загруженный им Google tag вместе передали около 291 KB и заняли около 267 мс main thread; Lighthouse также помечал около 195–200 KB JavaScript как неиспользуемые во время начальной загрузки. Переносить GTM после согласия без отдельной проверки аналитики нельзя: это меняет недавно настроенную схему измерения.

## Размер ответа

Один прямой HTTPS-запрос на каждую страницу с `Accept-Encoding: br,gzip`. `wire` — размер сжатого ответа, `HTML` и вложенные части — байты после распаковки. Встроенный RSC измерен внутри HTML; отдельный RSC-запрос в этом пробном вызове вернул 307 и не принят как показатель размера.

| Страница | HTML | wire (Brotli) | встроенные RSC scripts | inline CSS |
|---|---:|---:|---:|---:|
| `/` | 1 179 280 B | 312 928 B | 649 672 B | 194 119 B |
| `/leistungen/webdesign-halle` | 665 866 B | 183 745 B | 390 230 B | 194 119 B |
| `/leistungen/website-erstellen-lassen` | 675 129 B | 185 526 B | 395 531 B | 194 119 B |

Встроенный RSC и общий inline CSS объясняют большую часть несжатого HTML. В `next.config.mjs` включён `experimental.inlineCss`, который убирает отдельный блокирующий CSS-запрос; выключать его только ради уменьшения HTML без парного LCP-замера рискованно. Корневой `NextIntlClientProvider` получает полный файл сообщений языка — это кандидат для отдельного измерения объёма сериализации. Серверный текст, переводы и SEO-метаданные сохраняем.

## HTTPS и www

Проверка сертификата обоих хостов прошла: SAN содержит `saaleweb.de` и `www.saaleweb.de`, срок до 06.11.2026. До исправления `http://www.saaleweb.de/leistungen/webdesign-halle?utm_source=t1&check=1` давал 301 на тот же `https://www` URL и затем 200; `https://www` напрямую тоже давал 200. `http://saaleweb.de` уже давал 301 на канонический HTTPS.

В `next.config.mjs` добавлен host-specific постоянный 308 для `www.saaleweb.de` → `saaleweb.de` с сохранением пути и query. Локальный production-сервер подтвердил 308 для `/`, EN и RU service URL; канонический хост остался 200. После деплоя `3732632` production дал тот же результат для главной, DE/EN/RU страниц услуг и GET-запроса с параметрами. Прямой `https://www` делает один переход 308 к каноническому HTTPS и 200; `http://www` сначала получает существующий 301 на HTTPS www, затем 308 на основной домен и 200. Цикла нет. Для Google постоянный серверный редирект — сильный сигнал предпочитаемого URL; см. [рекомендации Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls). Поведение `has: host`, кода 308 и передачи query соответствует [документации Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects).
